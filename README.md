# Booking Service — сервис бронирования переговорных комнат

Backend-приложение на **FastAPI** для управления переговорными комнатами и бронированиями. Поддерживает регистрацию сотрудников, JWT-аутентификацию, разграничение прав администратора и сотрудника, проверку доступности временных слотов и защиту от конфликтующих бронирований.

Проект разработан как тестовое задание и доработан с акцентом на безопасность API, тестирование и воспроизводимое развёртывание через **Docker Compose**.

## Возможности

- Регистрация сотрудников и вход с использованием JWT Bearer-токена.
- Безопасное создание первого администратора через отдельную CLI-команду, без публичной регистрации с ролью `admin`.
- Просмотр и изменение профиля; управление пользователями и ролями для администратора.
- Запрет понижения последнего администратора.
- Просмотр комнат и свободных временных слотов на выбранную дату.
- Создание, просмотр и отмена бронирований с разграничением доступа по владельцу.
- Просмотр и фильтрация всех бронирований по дате для администратора.
- Защита от двух активных бронирований одного слота с помощью ограничения уникальности в PostgreSQL.
- Защита от конкурентной повторной отмены бронирования посредством `SELECT ... FOR UPDATE`.
- Автоматическая проверка приложения тестами **перед запуском рабочего API**.

## Быстрый старт: Docker Compose

**Необходимое ПО:** Docker Desktop с Docker Compose. Для работы с исходным кодом удобно использовать PyCharm; устанавливать Python и PostgreSQL на компьютер для запуска через Docker необязательно.

### 1. Подготовьте переменные окружения

В корне проекта создайте `.env` из примера. В терминале PowerShell:

```powershell
Copy-Item .env.example .env
```

Откройте `.env` и задайте свои значения. Пример структуры:

```dotenv
POSTGRES_USER=postgres
POSTGRES_PASSWORD=REPLACE_WITH_STRONG_DB_PASSWORD
POSTGRES_DB=booking_db
POSTGRES_HOST=localhost
POSTGRES_PORT=3223

JWT_SECRET=REPLACE_WITH_A_RANDOM_SECRET_AT_LEAST_32_BYTES
JWT_ALGORITHM=HS256
JWT_EXP_DELTA_SECONDS=3600
```

**Обязательно замените** `POSTGRES_PASSWORD` и `JWT_SECRET` на собственные секреты. JWT-секрет должен содержать **не менее 32 байт UTF-8**. Сгенерировать его можно командой:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Вставьте полученную строку вместо `JWT_SECRET` в `.env`. **Файл `.env` не добавляйте в Git.**

`POSTGRES_PORT` — порт PostgreSQL на компьютере (в примере `3223`). Внутри Docker используются `db:5432` для рабочей базы и `test_db:5432` для тестовой. Значения `POSTGRES_HOST` и `POSTGRES_PORT` внутри контейнеров задаются Docker Compose.

### 2. Соберите образы и запустите приложение

```powershell
docker compose up --build --force-recreate --wait app
```

Это **основная команда проверяемого запуска**. Docker Compose запускает тестовую БД, выполняет тесты и **только при их успешном завершении** разрешает запуск рабочего приложения.

Опция `--force-recreate` обеспечивает повторный запуск тестового контейнера, в том числе после предыдущего успешного тестирования. `--wait` дожидается готовности рабочего сервиса.

> **Важно при обновлении:** этот способ рассчитан прежде всего на локальное развёртывание и проверку. `--force-recreate` может перезапустить уже работающее приложение; автоматический rollback предыдущей версии не реализован. Для production-обновлений без простоя нужен отдельный процесс развёртывания.

### 3. Проверьте состояние

```powershell
docker compose ps -a
```

После успешного запуска ожидается:

| Сервис | Назначение | Состояние |
|---|---|---|
| `test_db` | Изолированная PostgreSQL для тестов | `healthy` |
| `tests` | Временный FastAPI + pytest | `Exited (0)` |
| `db` | Рабочая PostgreSQL | `healthy` |
| `app` | Рабочий FastAPI | `healthy` |

Проверить результат тестов и логи приложения:

```powershell
docker compose logs tests
docker compose logs app
```

### 4. Откройте API

- **Swagger UI:** http://localhost:8000/docs
- **OpenAPI:** http://localhost:8000/openapi.json
- **Базовый адрес:** http://localhost:8000

После завершения тестов контейнер `test_db` можно остановить для экономии ресурсов:

```powershell
docker compose stop test_db
```

Это **не остановит** рабочие `app` и `db`. Тестовая БД будет снова запущена при необходимости. Docker Compose не останавливает её автоматически после выполнения pytest.

## Как устроена проверка при запуске

В проекте используется **один постоянный контейнер приложения — `app`**. Отдельного сервиса `test_app` нет.

1. `test_db` запускает изолированный PostgreSQL.
2. В контейнере `tests` временно поднимается Uvicorn с тем же FastAPI-приложением и подключением **только к `test_db`**.
3. После готовности HTTP API запускается полный набор pytest.
4. Временный сервер останавливается, а контейнер `tests` завершается с кодом `0` при успехе или ненулевым кодом при ошибке.
5. `db` ожидает успешного завершения `tests` через `depends_on: condition: service_completed_successfully`.
6. `app` стартует после успешной проверки и готовности рабочей PostgreSQL.

**Если тесты не прошли, рабочее приложение не запускается при новом развёртывании.** Запуск тестов не изменяет рабочую базу: тестовая БД использует отдельный контейнер и имя `test_db`. В начале интеграционного набора фикстуры пересоздают начальные тестовые данные (комнаты, слоты, администратора).

В целях безопасности очистка таблиц разрешается только при `ALLOW_TEST_DB_RESET=1` и настройках `POSTGRES_DB=test_db`, `POSTGRES_HOST=test_db`.

> Это **проверка перед стартом**, а не постоянный мониторинг тестами. Если приложение уже развёрнуто, Compose сам по себе не обеспечивает безопасный откат неудачного обновления.

## Управление контейнерами

Просмотр состояний:

```powershell
docker compose ps -a
```

Остановить и удалить контейнеры проекта:

```powershell
docker compose down
```

Основная БД хранится в постоянном Docker volume `postgres_data`, поэтому `docker compose down` **не удаляет** её данные.

**Опасная команда — полностью удаляет данные основной БД:**

```powershell
docker compose down -v
```

Не выполняйте её, если хотите сохранить пользователей и бронирования.

## Создание первого администратора

Публичная регистрация через `POST /register` **всегда назначает роль `employee`**. Первый пользователь с ролью `admin` создаётся отдельно через CLI после успешного запуска приложения:

```powershell
docker compose exec app python -m app.bootstrap_admin
```

Команда интерактивно запросит имя пользователя, email и пароль. Пароль вводится без отображения символов, а в БД хранится его bcrypt-хеш.

Если администратор уже существует, команда откажет в повторной инициализации. Доступ к Docker и CLI администратора должен быть только у доверенного оператора.

Тестовый администратор `test_first_admin`, используемый pytest, **не создаётся в рабочей базе**.

## Роли и права

| Операция | `employee` | `admin` |
|---|:---:|:---:|
| Просмотр собственного профиля | Да | Да |
| Обновление собственного профиля | Да | Да |
| Получение списка пользователей | Нет | Да |
| Получение и изменение чужого профиля | Нет | Да |
| Изменение ролей пользователей | Нет | Да |
| Просмотр комнат и доступных слотов | Да | Да |
| Создание бронирования | Да | Да |
| Просмотр своих бронирований | Да | Да |
| Просмотр всех бронирований | Нет | Да |
| Отмена собственной брони | Да | Да |
| Отмена чужой брони | Нет | Да |

Дополнительно запрещено снимать роль у **последнего администратора**. Авторизация проверяет реальные права пользователя по данным БД, а не только по содержимому JWT.

## HTTP API

Авторизованные маршруты требуют заголовок:

```http
Authorization: Bearer <access_token>
```

### Регистрация и вход

| Метод | Маршрут | Описание |
|---|---|---|
| `POST` | `/register` | Регистрация сотрудника |
| `POST` | `/login` | Получение JWT |

Пример запроса регистрации:

```json
{
  "username": "employee_user",
  "email": "employee@example.com",
  "password": "password123",
  "phone": null
}
```

Успешная регистрация возвращает данные пользователя с ролью `employee` без пароля или его хеша.

Пример входа:

```json
{
  "username": "employee_user",
  "password": "password123"
}
```

Ответ:

```json
{
  "access_token": "<jwt_token>",
  "token_type": "bearer"
}
```

### Пользователи

| Метод | Маршрут | Доступ |
|---|---|---|
| `GET` | `/users/self` | Авторизованный пользователь |
| `GET` | `/users` | Администратор |
| `GET` | `/users/{user_id}` | Администратор |
| `PATCH` | `/users/{user_id}` | Владелец; администратор может изменять других |

Пример частичного обновления:

```json
{
  "phone": "79998887766"
}
```

Неуказанные поля остаются без изменений. Сотрудник не может изменить собственную роль.

### Комнаты

| Метод | Маршрут | Описание |
|---|---|---|
| `GET` | `/rooms` | Список комнат |
| `GET` | `/rooms/{room_id}` | Информация о комнате |
| `GET` | `/rooms/available/{date}` | Доступные слоты на дату |

Пример: `GET /rooms/available/2030-01-15`.

При первоначальном запуске создаются три комнаты: большой конференц-зал (до 25 человек), средний (до 15) и малый (до 8). У каждой по три временных слота: **09:00–12:00**, **13:00–16:00**, **16:00–19:00**. При повторном старте уже существующие комнаты не дублируются.

### Бронирования

| Метод | Маршрут | Доступ / назначение |
|---|---|---|
| `POST` | `/bookings` | Создание бронирования |
| `GET` | `/bookings` | Список собственных бронирований |
| `GET` | `/bookings/{booking_id}` | Своя бронь или любая для администратора |
| `GET` | `/bookings/all` | Все бронирования; только администратор |
| `PATCH` | `/bookings/cancel/{booking_id}` | Отмена своей брони или любой для администратора |

Пример создания бронирования:

```json
{
  "room_id": 1,
  "time_window_id": 1,
  "date": "2030-01-15"
}
```

> `time_window_id` должен принадлежать указанной комнате. Получить подходящие идентификаторы можно через `/rooms/available/{date}`.

Администратор может фильтровать бронирования по дате: `GET /bookings/all?date=2030-01-15`.

Отмена не удаляет запись из БД: `is_active` становится `false`, сохраняются время отмены и инициатор, а слот снова доступен для бронирования.

Основные HTTP-коды ошибок: `401` — нет действительной авторизации, `403` — недостаточно прав, `404` — объект не найден, `409` — конфликт уникальности или бронирования, `422` — ошибка валидации. Для отдельных ошибок бизнес-правил используется `400`.

## Тестирование

В проекте **172 тестовых случая** (последний подтверждённый полный прогон). Тесты разделены по назначению:

- `tests/unit/` — unit-тесты сервисов, авторизации, транзакций и ошибок с помощью моков, без реальных HTTP-запросов.
- `tests/integration/` — запросы к работающему API, проверка ролей и JWT, валидации, бронирований, ошибок, конкуренции и отмены.
- `tests/conftest.py` — общие фикстуры, генерация тестовых пользователей и подготовка данных.

### Запуск полного набора отдельно от рабочего приложения

```powershell
docker compose up --build --force-recreate --abort-on-container-exit --exit-code-from tests tests
```

Временный сервер стартует непосредственно внутри `tests`; рабочая БД и рабочее приложение для этого запуска не нужны. Результат выполнения возвращается в коде завершения контейнера `tests`.

### Только unit-тесты

Если тестовый Docker-образ уже собран, unit-тесты можно запустить без PostgreSQL:

```powershell
docker compose run --rm --no-deps --entrypoint python tests -m pytest -q tests/unit
```

### Проверка стабильности

В ходе доработки полный набор из 172 тестов успешно прошёл **три последовательных запуска**. Тестовая БД автоматически приводится к начальному состоянию перед каждым интеграционным прогоном.

## Локальная разработка без Docker

Для локального запуска необходимы **Python 3.13**, Poetry и доступная PostgreSQL с заранее созданной базой. В `.env` укажите локальные `POSTGRES_HOST` и `POSTGRES_PORT`, соответствующие реальному подключению.

```powershell
poetry install
poetry run uvicorn app.app:app --reload
```

Локальный запуск Uvicorn **не выполняет автоматическую проверку pytest перед стартом**: этот сценарий реализован в Docker Compose.

## Важные ограничения

- Схема БД создаётся через SQLAlchemy при старте; система миграций версий схемы пока не добавлена.
- Проверка тестами при запуске не заменяет отдельную стратегию production-деплоя с резервным копированием, миграциями и откатом.
- `GET /openapi.json` используется как HTTP healthcheck приложения; это не полноценная проверка всех внешних зависимостей.
- Секреты должны храниться вне репозитория, в том числе нельзя публиковать `.env` и рабочие токены.
