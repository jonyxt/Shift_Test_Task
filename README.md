# Booking Service — сервис бронирования переговорных комнат

Backend-приложение на **FastAPI** для управления переговорными комнатами и бронированиями. Реализованы регистрация сотрудников, JWT-аутентификация, разграничение прав, проверка доступности слотов, защита от конкурентных бронирований и отмена брони с сохранением истории.

Проект создан как тестовое задание и доработан с акцентом на безопасность API, автоматизированное тестирование и воспроизводимое развёртывание с **Docker Compose**, **Alembic** и **PostgreSQL**.

## Возможности

- Регистрация сотрудников с ролью `employee` и вход по JWT Bearer-токену.
- Безопасное создание первого администратора отдельной CLI-командой (через публичный API роль `admin` получить нельзя).
- Управление пользователями и ролями; запрет понижения последнего администратора.
- Разграничение прав доступа к профилям и бронированиям.
- Получение списка комнат и свободных временных слотов на выбранную дату.
- Создание и отмена бронирований; отмена не удаляет историю.
- Предотвращение двойного бронирования через частичный уникальный индекс PostgreSQL.
- Защита от конкурентной повторной отмены с помощью `SELECT ... FOR UPDATE`.
- Версионирование схемы БД через Alembic.
- Инициализация стандартных переговорных комнат и слотов отдельной командой.
- Проверка тестов в изолированной БД до запуска рабочего приложения при запуске через Compose.

## Быстрый старт через Docker Compose

**Понадобятся:** Git, Docker Desktop (Windows/macOS) или Docker Engine с Compose (Linux). Для запуска в контейнерах устанавливать Python, Poetry и PostgreSQL на хост не требуется.

### 1. Получение проекта

```powershell
git clone https://github.com/jonyxt/Shift_Test_Task.git
cd Shift_Test_Task
```

### 2. Настройка окружения

Создайте локальный файл `.env` из шаблона:

```powershell
Copy-Item .env.example .env
```

Для Linux/macOS:

```bash
cp .env.example .env
```

Пример основных настроек:

```dotenv
APP_ENV=dev

POSTGRES_USER=postgres
POSTGRES_PASSWORD=REPLACE_WITH_STRONG_DB_PASSWORD
POSTGRES_DB=booking_db
POSTGRES_HOST=localhost
POSTGRES_PORT=3223

JWT_SECRET=REPLACE_WITH_A_RANDOM_SECRET_AT_LEAST_32_BYTES
JWT_ALGORITHM=HS256
JWT_EXP_DELTA_SECONDS=3600
```

Обязательно замените `POSTGRES_PASSWORD` и `JWT_SECRET`. Для генерации случайного JWT-секрета можно использовать Python:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Скопируйте результат в `JWT_SECRET`. Приложение требует секрет длиной **не менее 32 байт UTF-8**. Не добавляйте `.env` в Git и не публикуйте рабочие пароли или токены. `.env.example` содержит только образцы значений.

`POSTGRES_HOST=localhost` и `POSTGRES_PORT=3223` используются при локальном запуске Python на хосте. Внутри Docker Compose параметры подключения переопределены: `db:5432` для рабочей БД, `test_db:5432` для тестовой.

Режимы `APP_ENV`:

| Режим | Назначение | Особенности |
| --- | --- | --- |
| `dev` | Локальная разработка | Значение по умолчанию |
| `test` | Тестовый API и pytest | Разрешена только БД `test_db` на хосте `test_db` |
| `prod` | Рабочее окружение | Запрещена тестовая БД и некоторые демонстрационные секреты |

`APP_ENV=prod` **сам по себе не делает приложение готовым к размещению в интернете**: для настоящего production дополнительно нужны HTTPS/reverse proxy, ограничение доступа к портам и БД, резервные копии, мониторинг и безопасный процесс обновления.

### 3. Сборка и запуск

```powershell
docker compose up --build --force-recreate --wait app
```

При проверяемом запуске Compose выполняет следующую последовательность:

1. `test_db` — поднимает отдельный PostgreSQL для тестов.
2. `tests` — применяет миграции Alembic к тестовой БД, запускает временный HTTP API и полный набор pytest. При ошибке завершает работу с ненулевым кодом.
3. `db` — запускает рабочую PostgreSQL после успешного завершения тестов.
4. `migrate` — выполняет `alembic upgrade head` в рабочей БД.
5. `seed` — добавляет недостающие стандартные комнаты и слоты.
6. `app` — запускает FastAPI после успешного выполнения миграций и инициализации.

При ошибке тестов, миграций или инициализации зависимые сервисы не должны запускаться как успешно подготовленное приложение. **Тесты не обращаются к рабочей БД.** `--force-recreate` нужен для повторного выполнения одноразового сервиса тестов при последующих проверяемых запусках.

> Важно: это схема проверяемого старта проекта, а не полноценный CI/CD-конвейер. Повторное развёртывание может перезапустить API; автоматического отката к предыдущей версии приложения и схемы БД здесь нет.

### 4. Проверка состояния

```powershell
docker compose ps -a
docker compose logs tests
docker compose logs migrate
docker compose logs seed
docker compose logs app
```

Ожидаемые состояния после успешного запуска:

| Сервис | Состояние |
| --- | --- |
| `test_db` | `healthy` |
| `tests` | `Exited (0)` |
| `db` | `healthy` |
| `migrate` | `Exited (0)` |
| `seed` | `Exited (0)` |
| `app` | `healthy` |

После запуска доступны:

- Swagger UI: http://localhost:8000/docs
- OpenAPI: http://localhost:8000/openapi.json
- API: http://localhost:8000

Текущий Docker healthcheck использует `/openapi.json` и подтверждает доступность HTTP-сервера, **но не является полноценной проверкой готовности всех зависимостей**.

### 5. Создание первого администратора

После запуска приложения выполните:

```powershell
docker compose exec app python -m app.bootstrap_admin
```

CLI интерактивно запросит имя, email и пароль. Пароль вводится без отображения и хранится в БД только в виде bcrypt-хеша. Если администратор уже существует, команда не создаст второго первого администратора.

Публичный `POST /register` всегда создаёт пользователя с ролью `employee`. Тестовый администратор, создаваемый pytest, не попадает в рабочую БД.

## Тестирование

### Полный набор интеграционных и unit-тестов в Docker

```powershell
docker compose up --build --force-recreate --abort-on-container-exit --exit-code-from tests tests
```

Команда запускает изолированную `test_db`, применяет к ней миграции и запускает тестовый HTTP API с pytest. Ненулевой код завершения `tests` означает ошибку. Количество тестов может меняться по мере развития проекта.

Для просмотра результатов:

```powershell
docker compose logs tests
```

Для тестов предусмотрен защитный механизм: очистка таблиц допустима только при `ALLOW_TEST_DB_RESET=1`, `POSTGRES_DB=test_db` и `POSTGRES_HOST=test_db`. В основной рабочей БД тестовый сброс не выполняется.

### Только unit-тесты без PostgreSQL

Если Docker-образ сервиса `tests` уже собран:

```powershell
docker compose run --rm --no-deps --entrypoint python tests -m pytest -q tests/unit
```

Локально с установленным Poetry:

```powershell
poetry install
poetry run pytest -q tests/unit
```

Отдельные интеграционные тесты требуют подготовленного тестового окружения и тестового HTTP API; простой запуск полного `pytest` на хосте не заменяет Docker-сценарий.

## Управление миграциями Alembic

Схема PostgreSQL создаётся и обновляется через **Alembic**; FastAPI больше не вызывает `Base.metadata.create_all()`.

Первоначальная миграция: `c75bfc27cc29_initial_schema.py`. Она создаёт таблицы `users`, `rooms`, `time_windows`, `bookings`, связи и ограничения, PostgreSQL ENUM `user_role` и частичный уникальный индекс активных бронирований.

### Применение миграций

В Docker при обычном проверяемом запуске их автоматически применяет сервис `migrate`. Если рабочая БД уже запущена, команду можно выполнить отдельно:

```powershell
docker compose run --rm --no-deps migrate
```

### Просмотр текущей версии БД

```powershell
docker compose run --rm --no-deps migrate alembic current
```

### Проверка расхождений схемы

```powershell
docker compose run --rm --no-deps migrate alembic check
```

При полном соответствии ORM-моделям ожидается `No new upgrade operations detected.`

### Создание новой миграции при разработке

При доступной PostgreSQL, указанной в локальном `.env`:

```powershell
poetry run alembic revision --autogenerate -m "describe schema change"
```

**Каждую сгенерированную миграцию необходимо проверить вручную**, особенно операции с ENUM, индексами, ограничениями и удалением столбцов. Новый файл из `alembic/versions/` коммитится вместе с изменениями моделей. Затем миграция тестируется на отдельной БД и применяется командой:

```powershell
poetry run alembic upgrade head
```

Alembic хранит применённую ревизию в таблице `alembic_version` и при следующем обновлении выполняет только недостающие миграции.

> **Не запускайте `alembic downgrade base` на рабочей БД:** первоначальный откат удаляет все таблицы приложения вместе с данными. Перед потенциально опасными миграциями нужны резервная копия и план восстановления. `alembic stamp` следует использовать только при проверенном соответствии фактической схемы нужной ревизии.

## Инициализация начальных данных

Команда `app.seed_data` создаёт при необходимости три стандартные комнаты:

| Комната | Вместимость по описанию |
| --- | --- |
| Большой конференц зал | До 25 человек |
| Средний конференц зал | До 15 человек |
| Малый конференц зал | До 8 человек |

Для каждой комнаты добавляются временные слоты:

- `09:00–12:00`
- `13:00–16:00`
- `16:00–19:00`

Итого после первого запуска на пустой БД: **3 комнаты и 9 слотов**. Повторный запуск не дублирует существующие комнаты и слоты. Существующие описания комнат не перезаписываются; отсутствующие элементы стандартного набора могут быть восстановлены. Одновременное выполнение двух команд защищено advisory-блокировкой PostgreSQL.

Обычно инициализация запускается автоматически сервисом `seed` после `migrate`. При уже работающей БД её можно повторить вручную:

```powershell
docker compose run --rm --no-deps seed
```

Создание первого администратора **не входит** в seed и выполняется отдельно.

## Локальная разработка через PyCharm / Poetry

Для запуска вне контейнера используйте Python 3.13, Poetry и доступную PostgreSQL.

1. Создайте `.env` и задайте параметры подключения к PostgreSQL на хосте (`localhost:3223`, если база запущена через Compose).
2. Установите зависимости:

   ```powershell
   poetry install
   ```

3. При необходимости запустите только PostgreSQL в Docker:

   ```powershell
   docker compose up -d --no-deps db
   ```

4. Примените схему и создайте начальные данные:

   ```powershell
   poetry run alembic upgrade head
   poetry run python -m app.seed_data
   ```

5. Запустите FastAPI:

   ```powershell
   poetry run uvicorn app.app:app --reload
   ```

Локальный запуск Uvicorn сам по себе не запускает pytest и не применяет миграции: эти операции выполняются отдельно. Для проверки всего сценария развёртывания используйте Docker Compose.

## API

Все защищённые маршруты требуют заголовок:

```http
Authorization: Bearer <access_token>
```

### Регистрация и вход

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `POST` | `/register` | Регистрация сотрудника |
| `POST` | `/login` | Получение JWT-токена |

Пример регистрации:

```json
{
  "username": "employee_user",
  "email": "employee@example.com",
  "password": "password123",
  "phone": null
}
```

Пример входа:

```json
{
  "username": "employee_user",
  "password": "password123"
}
```

Ответ при успешном входе:

```json
{
  "access_token": "<jwt_token>",
  "token_type": "bearer"
}
```

### Пользователи

| Метод | Маршрут | Доступ |
| --- | --- | --- |
| `GET` | `/users/self` | Свой профиль |
| `GET` | `/users` | Только администратор |
| `GET` | `/users/{user_id}` | Только администратор |
| `PATCH` | `/users/{user_id}` | Свой профиль; администратор — другие профили и роли |

Сотрудник не может назначить себе роль администратора. Разрешения определяются по актуальным данным БД, а не только по JWT.

### Переговорные комнаты

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/rooms` | Список комнат |
| `GET` | `/rooms/{room_id}` | Данные комнаты |
| `GET` | `/rooms/available/{date}` | Свободные слоты на дату |

Пример: `GET /rooms/available/2030-01-15`.

### Бронирования

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `POST` | `/bookings` | Создание бронирования |
| `GET` | `/bookings` | Свои бронирования |
| `GET` | `/bookings/{booking_id}` | Своя бронь или любая для администратора |
| `GET` | `/bookings/all` | Все бронирования; только администратор |
| `PATCH` | `/bookings/cancel/{booking_id}` | Отмена своей или администратором любой брони |

Пример создания бронирования:

```json
{
  "room_id": 1,
  "time_window_id": 1,
  "date": "2030-01-15"
}
```

`time_window_id` должен принадлежать указанной комнате. Подходящие значения можно получить через `/rooms/available/{date}`.

Для администратора доступна фильтрация бронирований: `GET /bookings/all?date=2030-01-15`.

Отмена изменяет `is_active` на `false`, сохраняя время и инициатора отмены. Освободившийся слот можно снова забронировать.

Основные коды ошибок: `400` — нарушение бизнес-правила; `401` — требуется авторизация или токен недействителен; `403` — недостаточно прав; `404` — объект не найден; `409` — конфликт данных или бронирования; `422` — ошибка валидации.

## Управление Docker Compose и данными

```powershell
# Статус контейнеров проекта
docker compose ps -a

# Логи приложения
docker compose logs app

# Остановить контейнеры без удаления
docker compose stop

# Остановить и удалить контейнеры и сеть, сохранив данные БД
docker compose down
```

Рабочая PostgreSQL использует именованный том `postgres_data`, поэтому обычный `docker compose down` сохраняет пользователей и бронирования.

**Опасная команда — безвозвратно удаляет тома данных этого Compose-проекта:**

```powershell
docker compose down -v
```

Не используйте `down -v` при обычных обновлениях и остановке приложения.

## Ограничения и дальнейшее развитие

- Автоматические тесты при проверяемом запуске Compose не заменяют отдельный CI-процесс в GitHub Actions.
- Нет реализованного безопасного production-деплоя с резервным копированием перед изменениями схемы, управляемым обновлением, zero-downtime и автоматическим rollback.
- `GET /openapi.json` служит текущим HTTP healthcheck, а не полноценной проверкой готовности БД.
- Порты приложения и PostgreSQL публикуются Docker Compose; для размещения на публичном VPS необходимы ограничения доступа, HTTPS и пересмотр сетевой конфигурации.
- Начальные комнаты и слоты — демонстрационные данные. Их автоматическое восстановление следует учитывать при будущем добавлении административного редактирования комнат.
- Перед применением новых миграций к существующей рабочей БД необходимо проверять изменения и предусматривать резервную копию.
